## 2. Benchmark Scenarios

### Scenario A: Cold Start (App Boot with Dirty Banks)
> 測量應用啟動時存在待清理題庫（含極端快取遺失）之性能與恢復能力。

| 參數 | 規範數值 |
|------|---------|
| **測試情境** | 應用啟動，`mindspark_dirty_banks` 包含 5 個 Bank ID，其中 1 個本地題庫已被瀏覽器快取驅逐（`null`） |
| **預期行為** | 正常存在的 4 個題庫先 upsert 再刪除孤兒；快取遺失的 1 個題庫安全跳過並移出 dirty list，不發出雲端全刪請求 |
| **啟動時間目標** | 認證與資料抓取 < 1500ms，背景清理完成 < 3000ms |
| **驗收標準** | 應用 UI 不發生任何主線程卡頓，各 Bank 具備獨立 `try-catch` 容錯，雲端現存題目零遺失 |

### Scenario B: Steady-State Syncing (連續保存與縱深防禦)
> 標準運行狀態下的題庫儲存與同步效能。

| 參數 | 規範數值 |
|------|---------|
| **請求頻率** | 每 2 分鐘保存 1 次，每題庫約 50~100 題 |
| **預期延遲 (p95)** | `saveCloudQuestions` 總執行時間 < 1000ms |
| **縱深防禦驗證** | 孤兒刪除請求強制附加 `.eq('bank_id', bankId)`，確保刪除範圍嚴格受限 |
| **驗收標準** | 本地寫入 dirty 標記到移除 dirty 標記達成事務閉環，本地鎖定負擔 < 5ms |

### Scenario C: Peak Load (作答狂擊與題號雙鎖 - H1)
> 模擬極端高頻連擊 Enter 或快速連點選項之作答場景。

| 參數 | 規範數值 |
|------|---------|
| **互動頻率** | 10 次點擊/秒（或 100ms 內連續 10 次呼叫 `handleAnswer`） |
| **預期行為** | 第一次作答觸發計分與 SM-2 排程，`lastAnsweredQuestionIndexRef` 記錄當前題號；後續 9 次點擊因題號比對一致，100% 被靜默阻斷 |
| **解鎖驗證** | 用戶點擊「下一題」（`nextQuestion`）推進題目索引後，新題目立即開放正常作答 |
| **可接受錯誤率** | 0% 重複加分、0% 錯題庫重複灌入、0% SM-2 雙重計算 |

### Scenario D: Sustained Stress (多標籤頁鎖搶佔 - H3)
> 驗證 LocalStorage fallback 鎖在多分頁並發環境下的 TOCTOU 防禦。

| 參數 | 規範數值 |
|------|---------|
| **負載設定** | 3 個瀏覽器分頁同時以 1 秒為間隔觸發 `syncLocalToCloud` |
| **持續時間** | 5 分鐘壓力測試 |
| **隨機延遲** | 寫入 token 後隨機延遲 30~70ms 執行二次讀取確認 (Double-check) |
| **成功判據** | 同一時間區間內絕對只有 1 個分頁取得同步鎖，其餘分頁安全退出或重試，零鎖覆寫衝突 |

### Scenario E: Chaos / Fault Injection (混亂工程與容錯驗證)
> 注入極端運行期異常，檢驗防護機制的自癒能力。

| 故障注入類型 | 注入方式 | 持續狀態 | 預期防護行為 | 驗證缺陷 |
|------------|---------|---------|-------------|:--------:|
| **斷網中斷** | Upsert 成功後、Delete 執行前切斷網路 | 1 分鐘 | 本地 dirty 標記保留；網路重連後自動重試補傳與清理，達成最終一致性 | C1 |
| **快取驅逐 (Cache Eviction)** | 清除本機某題庫 `localStorage.removeItem('mindspark_bank_X')` 但 dirty 標記保留 | 永久 | 命中 `localQuestionsRaw === null` 守衛，記錄警告並自 dirty list 移除，**嚴禁發送全刪請求** | D7-001 |
| **離線分歧作答 (Divergent Offline)** | 裝置 A 離線完成 Chunk 0，裝置 B 離線完成 Chunk 1，兩裝置先後同步 | 永久 | 呼叫 `mergeChunkedPracticeSessions` 執行聯集合併，結果為 Chunk 0 與 1 皆 completed，保留 active draft | D7-002 |
| **分頁強制關閉** | 編輯節點文字後立即分頁關閉（觸發 `beforeunload`） | 瞬間 | `NodeEditPanel` 註冊的 `beforeunload` 即時將 pending debounce 內容 flush | D10-001 |
| **過期殭屍鎖** | 注入時間戳超過 30 秒前的 `mindspark_sync_lock_ts` | 永久 | 下一次同步判定鎖已超時過期，自動強制重置並安全獲取新鎖 | H3 |

## 4. Resource Contention Matrix

| 爭用資源 | 競爭模組 | 爭用型態 | 緩解與防禦機制 (Mitigation) |
|---------|---------|---------|----------------------------|
| **LocalStorage** | Tab A (Sync) vs Tab B (Sync) | 兩分頁同時寫入 fallback 鎖 token | 隨機延遲 (30~70ms) + 二次讀取驗證 (Double-check) 破壞對齊 |
| **React 作答事件** | 用戶連按 Enter vs 渲染批次 | 在切題反饋期間連續觸發 `handleAnswer` | 題號生命週期雙鎖（`lastAnsweredQuestionIndexRef` + `nextQuestion` 解鎖），脫離微任務 |

| **瀏覽器生命週期** | 頁面關閉 vs 500ms 防抖 | 用戶編輯後直接關閉視窗 | 註冊 `window.addEventListener('beforeunload', ...)` 強制同步 flush |

## 5. Benchmark Harness Specification

### 5.1 測試環境與工具鏈
- **單元與併發測試**：Vitest (`npm test`) 搭配 fake timers 與模擬 Storage / Supabase Client。
- **端對端壓力測試**：Playwright E2E (`npm run test:e2e`)，支援多 Browser Context 模擬跨標籤頁與多分頁並行。
- **型別與死碼檢查**：`npx tsc --noEmit` (Exit 0) 與 `npx knip` (零新增死碼)。

### 5.2 自動化執行協議 (Automated Execution Protocol)
1. **Concurrency Lock Test**:
   - 啟動 2~3 個並發上下文嘗試執行 `runWithSyncLock`。
   - 驗證僅有 1 個上下文能成功取得鎖並呼叫同步 API，其餘安全退避。
2. **Question Index Lock & Anti-Bounce Test**:
   - 在 100ms 內對 `handleAnswer` 連續發送 10 次作答請求。
   - 斷言作答狀態、分數與錯題記錄僅更新 1 次；呼叫 `nextQuestion` 後斷言新題目可正常作答。
3. **Chunk-level Set Union Merge Test**:
   - 建立兩組分歧的 Session 物件（Local: Chunk 0 completed; Cloud: Chunk 1 completed）。
   - 執行 `mergeChunkedPracticeSessions`，斷言結果包含 Chunk 0 與 Chunk 1 均為 completed，且保留各 Chunk 最高分與最晚時間戳。
4. **Cache Eviction Safe Guard Test**:
   - 在 `mindspark_dirty_banks` 中注入 Bank ID，但將其對應的本地題庫設為 `null`。
   - 執行 `retryCleanupDirtyBanks`，斷言 Supabase `delete` 函式未被呼叫，且該 Bank ID 成功自 dirty 清單移出。
5. **Tab Close BeforeUnload Flush Test**:
   - 掛載 `NodeEditPanel` 並觸發文字輸入（進入 debounce 期間）。
   - 派發 `beforeunload` 事件，斷言 `onUpdate` 立即被調用並傳入最新的輸入內容。
