## 2. Benchmark Scenarios

### Scenario A: Cold Start (首次載入)

> Measures initial startup and first-render performance.

| Parameter | Value |
|-----------|-------|
| **Description** | 載入包含 100 個節點的知識圖 |
| **Time to Interactive (TTI)** | < 1500ms |
| **Acceptance Criteria** | 畫面渲染無閃爍，節點位置立即可見 |

### Scenario B: Baseline (Steady-State 穩態操作)

> 正常編輯操作（新增節點、連線、修改文字）。

| Parameter | Value |
|-----------|-------|
| **Duration** | 5 minutes |
| **Action Pattern** | 每 10 秒新增一個節點並連接，雙擊編輯文字 |
| **Expected FPS** | 保持在 60 FPS |
| **Autosave Trigger** | 確認 `useGraphAutoSave` 不會引發主執行緒卡頓 (Main Thread Block < 16ms) |

### Scenario C: Peak Load (圖表複雜度極限)

> 測試 React Flow 與 Layout 演算法在極限節點數下的表現。

| Parameter | Value |
|-----------|-------|
| **Graph Size** | 200 個節點，300 條連線 (MAX_NODES 限制) |
| **Action** | 觸發「自動放射狀佈局 (applyAutoLayout)」 |
| **Expected Behavior** | 計算過程可能稍微掉幀，但不能導致瀏覽器標籤崩潰 (Crash) |
| **Max Acceptable Latency** | < 1000ms |

### Scenario D: Sustained Stress (Soak Test)

> 切換模式與大量 Undo/Redo，偵測記憶體洩漏與閉包陷阱。

| Parameter | Value |
|-----------|-------|
| **Action Pattern** | 執行「視覺模式」與「代碼模式」切換連續 100 次 |
| **Measurement** | 切換完成後的 JS Heap 大小 |
| **Memory Growth Tolerance** | < 5MB 成長 (允許少量快取，但須穩定) |
| **Success Criteria** | 沒有出現無盡迴圈，React 元件沒有卸載/掛載洩漏 |

### Scenario E: Chaos / Fault Injection (雲端異常測試)

> 測試 Supabase 同步與圖片上傳的故障容忍度。

| Fault Type | Injection Method | Expected Behavior | Recovery Time Target |
|------------|-----------------|--------------------|--------------------|
| 網路離線 | 開啟 Chrome Offline 模式 | 觸發 Autosave，成功寫入 LocalStorage，雲端同步進入 dirty fallback | 無縫，使用者不應感到卡頓 |
| Storage 拒絕上傳 | 修改 RLS 故意阻擋 | 顯示 Toast 錯誤，畫布節點不應崩潰 | 立即反應錯誤 |
| 時間戳衝突 | 模擬雲端有更新的資料 | 觸發分叉 (Fork) 機制（依據建議的修復方案） | 彈出對話框提示 |

## 5. Memory Leak Detection Protocol

針對重構後的 Hooks（特別是 `useGraphUndoRedo` 與 `useGraphAutoSave`）：
1. 建立一個 50 個節點的圖表。
2. 寫入一段腳本，每秒鐘改變一次節點位置（觸發 pushState）。
3. 執行 5 分鐘（產生 300 個 undo history）。
4. 觀察 Heap 快照，確認 `past` 陣列是否有容量限制（例如上限 50 步），超過的舊狀態是否被正確 Garbage Collected。
