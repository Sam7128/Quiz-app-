## 2. Benchmark Scenarios

### Scenario A: Cold Start (Lazy Load TipTap)

> 測量 TipTap 編輯器首次載入時的效能，驗證 `vendor-ui-core` chunk 拆分策略是否有效。

| Parameter | Value |
|-----------|-------|
| **Description** | 使用者首次點擊節點，觸發 GraphNotesPanel 渲染與 TipTap 實例化 |
| **First Render Target** | < 300ms |
| **Measurement Points** | 從 `onClick` 觸發到 TipTap `onTransaction` ready |
| **Acceptance Criteria** | 點擊後無明顯卡頓感，輸入框立即獲得焦點 |

### Scenario B: Baseline (Steady-State Typing)

> 測量代碼模式下，打字時的效能。

| Parameter | Value |
|-----------|-------|
| **Text Size** | 50 行 Markdown |
| **Typing Rate** | 模擬 300 CPM (Characters Per Minute) |
| **Auto-Update State** | OFF |
| **Expected Latency (p95)** | < 16ms (不掉幀) |
| **Expected Behavior** | 只有 GraphCodeEditor 重新渲染，GraphEditor 畫布不應重繪 |

### Scenario C: Peak Load (Markdown Parser Stress)

> 測量解析器與佈局演算法在處理複雜圖表時的極限。

| Parameter | Value |
|-----------|-------|
| **Data Volume** | 300 行 Markdown 列表，包含 10 層深度 |
| **Action** | 觸發 Auto-Update 或點擊手動更新 |
| **Expected Behavior** | `parseMarkdownToGraph` + `applyRadialLayout` + React Flow state update |
| **Max Acceptable Latency** | < 200ms 總計算時間 |
| **Failure Mode** | 必須截斷超出 200 節點的部分，但不能導致瀏覽器「Page Unresponsive」崩潰 |

### Scenario D: Sustained Stress (Soak Test - Debounce Accumulation)

> 測量 TipTap 長時間輸入時是否會導致記憶體洩漏或效能退化。

| Parameter | Value |
|-----------|-------|
| **Load Level** | 持續輸入並修改富文本筆記 10 分鐘 |
| **Measurement Interval** | 每 1 分鐘 |
| **Memory Growth Tolerance** | < 5MB growth (允許 undo 堆疊增長，但須有上限) |
| **Success Criteria** | 沒有 OOM，打字延遲維持在 <16ms |

### Scenario E: Chaos / Fault Injection (Storage Quota)

> 測試當 localStorage 容量滿時的系統彈性。

| Fault Type | Injection Method | Expected Behavior | Recovery Time Target |
|------------|-----------------|--------------------|--------------------|
| Quota Exceeded on Save | 塞入 5MB 垃圾資料填滿 localStorage | `saveGraph` 拋出警告 Toast，但 UI 不崩潰，使用者可繼續編輯並刪除其他圖表釋放空間 | 立即恢復（UI 不被 blocking） |
| Migration Failure | Mock migration 觸發 Error | 拋出 ErrorBoundary，提示使用者資料錯誤，防止回傳 `[]` 覆蓋 | 立即阻斷 |

### Scenario F: Data Scale Progression (Search Scope)

> 測量筆記搜尋功能隨節點數量的效能退化。

| Node Count | Expected Search Latency | Method |
|-------------|----------------------|--------|
| 10 nodes (1KB each) | < 10ms | Sync strip tags & match |
| 50 nodes (1KB each) | < 30ms | Sync strip tags & match |
| 200 nodes (1KB each) | < 100ms | Sync strip tags & match (若 >100ms，需改為 Web Worker 或非同步 yield 處理) |

## 3. Warm-up Curve Specification

> Vite 開發伺服器與生產環境的載入差異。由於是純前端系統，Warm-up 主要指的是 React 的首屏渲染與 TipTap 的非同步資源載入。

**Acceptance Criteria**:
- 載入帶有 TipTap 的 chunk (`vendor-ui-core`) 的時間 < 500ms（在 Fast 3G 網路下需 < 3s）
- 首屏可互動時間 (TTI) < 1.5s

## 4. Resource Contention Matrix

| Resource | Competing Modules | Contention Pattern | Risk Level | Mitigation |
|----------|-------------------|-------------------|------------|------------|
| LocalStorage | `GraphEditor` vs `QuizEngine` | 兩者同時 autosave，若遇到配額不足，可能導致一方儲存失敗 | 🟠 HIGH | 實作全域 `StorageManager` 監控配額，當剩餘空間 < 500KB 時停止保存低優先級快取 |
| Main Thread (CPU) | `TipTap` vs `React Flow` | 在切換模式的瞬間，TipTap 的銷毀與 React Flow 的大量節點渲染同時發生 | 🟡 MEDIUM | 使用 `React.startTransition` 或 `setTimeout` 分散計算壓力 |

## 5. Benchmark Harness Specification

### Execution Protocol (Manual QA via Browser DevTools)
1. **環境**: Chrome (最新版) 隱身模式（無擴充套件干擾），CPU Throttle 設為 4x slowdown。
2. **Setup**: 在 `mindspark_graphs` 中注入 150 個節點的測試 JSON。
3. **Run Scenario A**: 點擊節點，觀察 Profiler 中的 TipTap 渲染時間。
4. **Run Scenario B**: 在代碼模式輸入，觀察 React DevTools Profiler，確認 `GraphEditor` 沒有無意義的 re-render。
5. **Run Scenario C**: 貼上 300 行 Markdown，觀察 Main Thread 阻塞時間。
6. **Run Scenario E**: 執行 `localStorage.setItem('junk', 'a'.repeat(4.5 * 1024 * 1024))`，然後在面板中打字觸發 autosave，驗證 UI 反應。
