## 2. Benchmark Scenarios

### Scenario A: Cold Start (AI Config Loading)

> 衡量首次讀取加密 AI 設定時的非同步解密效能。

| Parameter | Value |
|-----------|-------|

| **First Request Latency Target** | < 20ms |

> 標準戰鬥模式下的狀態持久化效能。

> 模擬使用者在 UI 卡頓或蓄意破壞時的快速連點。

| Parameter | Value |
|-----------|-------|

## 5. Memory Leak Detection Protocol

> **Purpose**: 驗證非同步的 WebCrypto 調用與 Promise 是否被正確回收。

### Test Procedure
1. 在戰鬥模式中開啟自動答題腳本，持續運行 1 小時 (約 1800 題)。
2. 使用 Chrome DevTools Memory Profiler 每 10 分鐘進行 Heap Snapshot。

### Leak Detection Criteria
| Metric | Pass | Fail |
|--------|------|------|
| Detached Promise 回收 | 無孤立 Promise | 存在未解析或未回收的 Promise 鏈 |
| Heap Growth (after GC) | < 1MB / hr | > 5MB / hr |

## 9. Benchmark Harness Specification

### 9.1 Execution Protocol

1. **環境準備**: 啟動本地 Vite 開發伺服器 (`npm run dev`)。
2. **連點壓力測試**: 在終端機執行 Playwright E2E 腳本，模擬對 `QuizCard` 選項 1 秒內進行 20 次連點，驗證僅有 1 次有效送出。
3. **RPC 攔截測試**: 透過 Playwright 網路攔截，阻斷 `/rpc/submit_challenge_score` 路由，確認前端沒有發送 fallback 的 `UPDATE` 請求。
4. **狀態競爭測試**: 撰寫腳本在 100ms 內對 `useBattleSystem` 觸發 5 次狀態變更，驗證最終 localStorage 內的 `mindspark_battle_state` 與 `mindspark_battle_state_sig` 是相符的。

### 9.2 Success Criteria Summary

| Scenario | Pass Criteria | Fail Criteria |
|----------|--------------|---------------|
| Quiz 連點防護 | 20 次點擊只觸發 1 次 API 呼叫，且出錯後可重試 | 多次 API 呼叫，或出錯後按鈕永久死鎖 |
| RPC Fallback | 網路阻斷時系統終止操作並顯示錯誤 | 系統降級使用舊版邏輯更新資料庫 |
| 狀態簽名競爭 | 高頻更新後，手動重整頁面能成功通過簽名驗證 | 重整後因簽名不匹配而回退至初始狀態 |
