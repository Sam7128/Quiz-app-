# 知識圖 / 視覺化筆記功能探索整理

日期：2026-03-08  
專案：MindSpark / Quiz-app--main  
用途：交給後續負責「創造計劃」的 AI 作為前置探索摘要

## 1. 這份文件的目的

這份文件不是最終規格，也不是實作說明，而是基於目前程式實際結構做出的探索結論。  
目的是幫規劃 AI 直接理解：

- 這個想法是否適合現在的產品
- 哪些地方和現有架構相容
- 哪些地方容易被想得太簡單
- 功能應該如何切分，才不會傷到原本的刷題體驗
- 新增的「全部攤開 / 逐步點開」應該怎樣定義

---

## 2. 高層結論

### 2.1 是否適合這個產品

適合，而且方向上是合理的。

目前產品核心是：

- 題庫管理
- 測驗練習
- 錯題回顧
- AI 輔助出題 / 助教
- 遊戲化學習

如果加入「視覺化知識圖 / 筆記圖」，它不是偏題，而是把產品從：

- 只負責「測驗與檢驗」

延伸到：

- 「整理知識」
- 「結構化理解」
- 「從練習到內化」

也就是說，這個功能不是炫技插件，而是學習閉環的一部分。

### 2.2 是否會影響原本功能

如果切分得對，影響可以很小。  
如果 scope 一開始就過大，反而很容易拖慢主流程。

真正的關鍵不是「能不能加」，而是：

- 要不要把它當成獨立工作區
- 要不要把它做成 Beta / 實驗室功能
- 要不要把 Mermaid 降成匯入匯出格式，而不是主互動模型

---

## 3. 目前專案實際狀況

以下是與這個功能最有關的現況。

### 3.1 App 是用 view 切頁，不是複雜路由

目前 `AppView` 很單純：

- `dashboard`
- `quiz`
- `mistakes`
- `manager`
- `guide`
- `social`

參考：

- `types.ts`
- `App.tsx`
- `components/AppContent.tsx`

這代表新功能最自然的整合方式是：

- 新增一個獨立 view
- 例如 `graph` / `knowledge_graph`

而不是把它硬塞進 `BankManager` 或 `AIPromptGuide`。

### 3.2 現有資料層是乾淨的，適合加新資料域

目前 repository 已經分成：

- `LocalStorageRepository`
- `CloudStorageRepository`

且透過 `IStorageRepository` 統一介面管理。

參考：

- `services/repository.ts`
- `services/localRepo.ts`
- `services/cloudRepo.ts`

這非常重要，因為它代表知識圖資料可以獨立成一個新資料域，不需要和題目資料混在一起。

### 3.3 設定頁與全域 modal 已經有入口模式

現在設定 modal 是透過：

- `App.tsx`
- `components/GlobalModals.tsx`
- `components/Settings.tsx`

來管理。

所以如果要加 Beta 開關，現有結構足夠承接。  
但要注意：目前 `gameMode` 不是存在 `UserSettings`，而是獨立存在 storage key。

這表示規劃時要先決定：

- 知識圖 Beta 開關要走 `UserSettings`
- 還是像 `gameMode` 一樣走獨立 key

不要規劃得模糊。

### 3.4 現在沒有看到重型功能的懶載入實踐

目前沒看到 `React.lazy` / `Suspense` 的實際使用。

這代表如果直接引入大型圖形編輯套件，主 bundle 很可能變重。  
因此規劃時必須明寫：

- 圖編輯器頁面要 feature-level code splitting
- 只有進入該頁時才載入大型依賴

這不是實作細節，而是必須進 proposal / design 的要求。

### 3.5 現有產品語言本來就接受「漸進揭露」

現有 UI 已經有兩種跟這次需求很接近的模式：

- 單一卡片展開收合：`components/RecentMistakesCard.tsx`
- 按需顯示提示 / 解析：`components/QuizCard.tsx`

這代表新功能加上「全部攤開 / 逐步點開」是合理的，不會違反產品既有互動風格。

## 4. 對先前構想的修正結論

## 4.1 對的部分

先前構想裡以下幾點是對的：

- 用 Beta / 測試模式隔離新功能
- 使用現成節點編輯引擎，不要從零寫
- 把 Mermaid 定位成支援格式，而不是唯一操作方式
- 主受眾是學生，目標是「專業但易用」
- AI 應該用來生成初稿，不應該成為唯一入口

## 4.2 過度樂觀的部分

以下幾點在規劃時不能再模糊帶過：

### A. 這不是單純加一頁

它其實是新增：

- 一個新資料域
- 一套新互動模型
- 一套新匯入匯出契約

### B. Mermaid 不適合當主資料格式

如果把 Mermaid 當主格式，之後會卡在：

- 手動編輯能力不足
- 節點層級資訊難表達
- 互動展開狀態難映射
- 匯入後很難保持可逆

比較合理的主格式應該是：

- Canvas JSON / Node-Edge JSON

Mermaid 只是：

- Import format
- Export format
- AI 溝通橋接格式

### C. 手機體驗不能被忽略

學生很多時候是手機使用者。  
但 node editor 在手機上很容易變成災難。

規劃時一定要先選一個立場：

- 桌面優先、手機唯讀
- 或手機只支援輕編輯

不要預設手機和桌面都完整可編輯。

### D. 不能一開始就把全部能力綁死在 v1

如果 v1 同時做：

- AI 生成
- 手動拖曳
- Mermaid 匯入
- Mermaid 匯出
- 模板樣式
- 題庫聯動
- 手機支援

那這不是 Beta，而是 scope 爆炸。

---

## 5. 建議的產品定位

最好的 framing 不是「Mermaid 功能」，而是：

> 知識圖工作區（Knowledge Graph Workspace / Visual Note Workspace）

其內部再支援：

- 手動建立
- AI 生成初稿
- Mermaid 匯入
- Mermaid 匯出

這樣使用者感受到的是：

- 我在整理知識

而不是：

- 我在學一套圖表語法

---

## 6. 關鍵互動模型：全部攤開 / 逐步點開

這是本次探索新增後，最值得保留的方向。

### 6.1 不應把它當成小功能開關

它不只是「展開收合」，而是在定義這個知識圖的閱讀哲學：

- `全部攤開`：看全貌、總複習、檢查完整性
- `逐步點開`：探索式學習、避免資訊過載、適合學生理解

因此，這兩者應該被定義成：

- 知識圖頁面的閱讀模式

而不是全域設定。

### 6.2 建議的模式分工

```text
知識圖工作區
├─ 編輯模式
│  ├─ 新增節點
│  ├─ 新增連線
│  ├─ 編輯文字
│  └─ 調整樣式
└─ 閱讀模式
   ├─ 全部展開
   └─ 逐步探索
```

### 6.3 建議的節點資訊分層

不要讓節點只有一層純文字。  
比較適合學生的作法是讓節點內容本身有層級：

- Level 1：標題
- Level 2：核心定義 / 關鍵概念
- Level 3：例子 / 補充 / 易錯點

然後對應兩種閱讀模式：

- `逐步探索`
  - 預設只顯示 Level 1
  - 點開才看到 Level 2 / Level 3

- `全部展開`
  - 一次顯示完整資訊

這比單純把整張圖顯示或隱藏更有學習價值。

### 6.4 建議的預設

建議預設：

- 閱讀模式預設為 `逐步探索`

原因：

- 比較符合學生學習
- 畫面壓力較小
- 比較接近現有產品的漸進揭露模式

`全部展開` 應作為明確切換選項存在工具列中。

## 7. 對現有程式的整合建議

## 7.1 入口層

建議做法：

- 在設定中加入 Beta / 實驗室功能開關
- 開啟後才出現知識圖頁入口
- 入口要同步出現在桌面與手機導覽

涉及位置：

- `components/Settings.tsx`
- `components/AppHeader.tsx`
- `components/MobileNav.tsx`
- `types.ts`
- `reducers/appReducer.ts`

### 注意

如果只改 header 不改 mobile nav，產品會出現不一致。  
這不是小問題，因為目前 mobile nav 本身就是主要入口之一。

## 7.2 View 層

建議新增：

- `AppView = ... | 'graph'`

然後在 `AppContent` 裡作為獨立內容區塊 render。

不要把圖功能直接塞進：

- `BankManager`
- `AIPromptGuide`
- `Dashboard`

因為那會把原本頁面責任搞混。

## 7.3 資料層

建議新增獨立資料模型，例如：

- `GraphDocument`
- `GraphNode`
- `GraphEdge`
- `GraphViewState`

至少要能表達：

- 文件 id / 名稱
- nodes / edges
- 節點位置
- 節點內容層級
- 展開狀態或閱讀偏好
- 建立與更新時間
- 可選的來源資訊（例如由 Mermaid 匯入、由 AI 生成）

### 核心原則

不要把圖資料混進題庫 schema。  
題目和圖可能會關聯，但不應該是同一種資料。

## 7.4 儲存策略

規劃 AI 必須先明確做出選擇：

- 圖表是 local only
- local first + cloud sync
- 或像錯題那樣裝置特定

現況上最穩妥的 v1 建議是：

- local first
- 暫不要求跨裝置完全同步

原因：

- 風險低
- 不影響現有雲端資料模型
- 可先驗證使用價值

## 8. AI 與 Mermaid 的正確定位

## 8.1 現有 AI 服務不適合直接承接圖表需求

目前 AI 服務主要面向：

- 題目 JSON
- PDF 出題
- 問答助教

參考：

- `services/ai.ts`
- `components/AIPromptGuide.tsx`
- `components/BankManager.tsx`

因此規劃不能直接假設：

- 既有 AI service 只要改一下 prompt 就能穩定產圖

這是不同契約。

## 8.2 AI 在知識圖功能中應扮演的角色

AI 最適合扮演：

- 產生知識圖初稿
- 幫學生把原始文本整理成節點結構
- 輸出某種受控格式

不適合扮演：

- 唯一的編輯方式
- 唯一的資料來源

## 8.3 Mermaid 的定位

Mermaid 比較適合做：

- AI 中介語言
- 匯入來源之一
- 匯出目的地之一

不適合做：

- 知識圖核心儲存格式
- 互動狀態的唯一承載者

## 8.4 Mermaid 支援應採「子集策略」

規劃時建議明寫：

- v1 只支援 Mermaid flowchart 的受控子集

不要承諾：

- 全 Mermaid 語法相容
- 雙向完美還原

否則 parser 和 exporter 很容易失控。

---

## 9. 風險清單

### 9.1 產品風險

- 功能過大，失去 Beta 應有的試驗性
- 主受眾其實只想刷題，導致入口雜訊增加
- 手機端操作太差，反而破壞專業感

### 9.2 技術風險

- 大型套件拉高 bundle size
- Mermaid parser 容錯不足
- 圖表 autosave 不完整導致資料遺失感
- 導覽、設定、資料層同時改動造成回歸風險

### 9.3 邏輯風險

- 不清楚圖表和題庫的關係
- 不清楚 Beta 開關是權限、偏好、還是頁面可見性
- 不清楚「全部展開 / 逐步探索」是文件層偏好還是使用者層偏好

---

## 10. 建議的 v1 切分

以下是比較務實的切法。

## Phase 1：最小可驗證版本

目標：

- 先證明這個工作區值得存在

內容：

- Beta 開關
- 獨立知識圖頁
- 手動新增節點
- 手動建立連線
- 基本文字編輯
- localStorage 保存
- 閱讀模式切換：
  - 全部展開
  - 逐步探索

先不要做：

- AI 生成
- Mermaid 匯入匯出
- 題庫聯動
- 跨裝置同步

## Phase 2：受控 Mermaid 匯入

目標：

- 驗證外部 AI 結果能否變成可編輯圖稿

內容：

- Mermaid flowchart 子集匯入
- 匯入錯誤提示與修正引導

## Phase 3：Mermaid 匯出

目標：

- 讓使用者能把成果帶去外部工具

內容：

- 受控子集匯出

## Phase 4：AI 生成初稿

目標：

- 把 AI 變成「起草器」

內容：

- 根據文本或學習資料生成圖稿
- 再轉為可編輯 canvas JSON

## Phase 5：與題庫 / 錯題聯動

目標：

- 讓知識圖和測驗閉環形成真正關聯

可能方向：

- 從錯題生成知識整理圖
- 為特定題庫建立對應知識圖

## 11. 給規劃 AI 的明確要求

請規劃 AI 在下一版計劃中務必回答以下問題，不要跳過：

1. 圖表是獨立資產，還是附屬於題庫？
2. 主資料格式是什麼？為什麼不是 Mermaid？
3. 手機端支援到什麼程度？
4. Beta 開關的語義是什麼？
5. `全部展開 / 逐步探索` 是頁面狀態、文件狀態，還是使用者偏好？
6. v1 明確不做哪些功能？
7. 套件載入策略如何保證不拖慢原本 app？
8. Mermaid 匯入支援哪些子集？
9. autosave 與離開頁面保護如何處理？
10. 系統清除資料（nuke）時是否包含知識圖？

如果這些問題沒有被答清楚，計劃仍然不夠成熟。

---

## 12. 對規劃 AI 的一句核心提醒

請不要把這件事規劃成「加一個 Mermaid 頁面」。  
正確的規劃對象應該是：

> 一個獨立的知識圖工作區，支援編輯模式與閱讀模式，閱讀模式包含「全部展開」與「逐步探索」，Mermaid 只是其中一種橋接格式。

## 13. 可利用的本地 skills（限 `.agents/skills`）

以下是這個功能最值得用的非 OpenSpec 類本地 skills。

### `ui-ux-pro-max`

用途：

- 幫知識圖頁定義清楚的互動與視覺語言
- 特別適合處理：
  - 編輯模式 vs 閱讀模式
  - 工具列密度
  - 資訊層級呈現
  - 學生導向的可讀性

### `performance`

用途：

- 為這個功能建立性能預算
- 避免大型圖形依賴拖慢整體 app
- 幫規劃文件明確要求：
  - feature-level code splitting
  - lazy loading
  - 大型元件只在進入知識圖頁時載入

### `react-testing-library`

用途：

- 將以下行為轉成可驗證測試：
  - 切換 `全部展開 / 逐步探索`
  - 點擊節點後內容展開
  - 編輯模式與閱讀模式切換
  - Beta 關閉時入口消失

這個 skill 對「避免規劃變成想像中的可用」特別重要。

### `frontend-security-coder`

用途：

- 針對 Mermaid 匯入、文字輸入、外部 AI 內容做前端安全界線思考
- 避免之後因為圖表文字、匯入內容、或外部資料造成 XSS / 不安全渲染

### `webapp-testing`

用途：

- 針對跨頁面操作、手機導覽、桌面導覽、modal/setting 流程做端到端驗證規劃

---

## 14. 最後的規劃建議

如果要讓這個功能真正適合現在的專案，請把它收斂成：

- 一個獨立知識圖工作區
- 一個小而可驗證的 v1
- 一套清楚的閱讀模式
- 一個以 Canvas JSON 為核心、以 Mermaid 為橋接的資料策略

最重要的是，不要讓這個功能一開始就搶走原本刷題產品的主角位置。  
它應該先是：

- 對進階學生有價值的 Beta 工作區

等證明價值後，再決定是否進一步成為產品主軸。
