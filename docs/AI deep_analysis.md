### 6. Storage 反序列化缺乏執行期型別驗證

`storage.ts` 的 `getBanksMeta()`、`getQuestions()`、`getMistakeLog()` 等函式，確實會把 `JSON.parse` 結果直接當成目標型別使用。

這是實際的資料邊界問題，但報告把它描述成「一定導致整頁白屏」過於誇張，因為解析失敗會被 catch，只有結構錯誤且後續存取欄位時才可能崩潰。

建議正確，但應以共用 schema/type guard 處理，不應只用 `.filter()` 靜默丟棄壞資料，否則可能造成資料無聲遺失。

### 7. UTC 日期造成台灣凌晨統計落到前一天

`analytics.ts` 使用：

```ts
new Date().toISOString().split('T')[0]
```

這確實是 UTC 日期，不是使用者本地日期。台灣凌晨至早上 7:59 的學習紀錄可能被歸入前一天。

此項為真實資料正確性缺陷，優先級 **P1**。應統一使用本地日期 helper，並補測 UTC+8 跨日案例。

### 8. 題庫匯出遺漏 SM-2 與錯題資料

`BankManager.tsx` 目前只匯出 `currentQuestions`，沒有匯出間隔重複資料或錯題紀錄。

「資料可攜性不完整」是正確的，但是否要把學習歷史綁在題庫 JSON 中，需要產品決策。更穩妥的是提供兩種格式：

- 題庫內容匯出
- 完整學習備份匯出

### 9. UTF-8 BOM 匯入風險確實存在

`BankManager.tsx` 直接將 `FileReader` 結果傳入 `JSON.parse`，沒有移除 BOM。Windows 編輯器產生的 BOM 可能造成 JSON.parse 失敗。

這是低成本、高實用性的修正，屬於 **P1**。

### 10. 生產包拆分問題確實存在

`vite.config.ts` 將 React、Recharts、Framer Motion、TipTap、ProseMirror 等都塞進 `vendor-ui-core`。現行 build 也實際產生約 1.3 MB 的 chunk。

報告的問題成立，但「一定會讓首頁多載入所有 TipTap」仍應用瀏覽器 Network trace 確認。改善方向合理：將 TipTap、Recharts 分離到真正使用它們的 lazy chunk。

## 二、問題存在，但報告嚴重度或原因需要修正

### 1. 登出後跨帳號污染

`AuthContext.tsx` 的 `signOut()` 確實沒有清理本地資料；本地題庫也不是 user-scoped。

這代表共用裝置存在隱私風險。然而報告說「下一個使用者登入後會無聲自動上傳」不完全正確。現行 `useBankManager.ts` 會檢查 `cloudSyncedAt`，並透過確認對話框詢問是否同步。

正確結論是：

> 存在跨帳號殘留與誤同步風險，但不是報告描述的完全無提示自動污染。

這仍是 **高優先級安全問題**，建議採用 user-scoped namespace，並在登出時提供「保留訪客資料／清除本機資料」選項。

### 2. `syncLocalToCloud` 重複建立雲端題庫

`cloudStorage.ts` 確實使用 `createCloudBank()` 建立新的雲端 ID，沒有真正的本地題庫與雲端題庫 ID 映射。

但目前成功同步後會寫入 `cloudSyncedAt`，因此透過正常 UI 重複同步並非「每次登入必然產生副本」。真正的問題是：

- 雲端 identity 映射不完整
- metadata 寫入失敗時可能重複
- 手動或其他呼叫路徑可能重新送出相同題庫

應列為 **P1 架構風險**，不是無條件 P0 災難。

### 3. SM-2 固定使用 4/1

`useQuizEngine.ts` 確實把答對映射為 4、答錯映射為 1。

但報告稱這是「偽算法」太強烈。標準 SM-2 本來就需要使用者評分；二元答題系統使用簡化評分是合理的第一版。真正問題是：

> 系統沒有區分猜對、快速答對、困難但答對等情況。

建議先加入「簡單／普通／困難」主觀評分或作答時間，而不是直接導入複雜 IRT。

### 4. `FocusTimer` 的背景節流

`FocusTimer.tsx` 使用 `setInterval` 每秒遞減，因此背景分頁節流造成計時顯示落後是合理風險。

但報告延伸到「限時測驗作弊」不適用，因為目前 FocusTimer 不是測驗倒數計時器。應只修正 FocusTimer 的 wall-clock 計時，不需要因此重做整個測驗系統。

### 5. AI JSON Schema 缺失

`ai.ts` 目前只是把 JSON schema 放進 prompt，沒有使用 Gemini 的原生 `responseSchema`。

問題成立，但「導入原生 schema 後 100% 合法 JSON」不成立。模型輸出仍需：

- 解析失敗處理
- 欄位驗證
- 題數與答案一致性驗證
- 選項與正解存在性驗證

建議有價值，但應避免宣稱百分之百保證。

### 6. 純文字題目不支援 Markdown、LaTeX、程式碼

`QuizCard.tsx` 確實以純文字節點渲染題幹、選項與解析，因此程式碼換行、公式、條列內容會受到限制。

這對 STEM 題庫是否重要，取決於目標使用者。目前應先支援安全的 Markdown/程式碼區塊；LaTeX 與 KaTeX 可作為後續選配，不宜直接列為核心 P0。

## 三、目前證據不足或建議過度的部分

以下內容目前不應直接當成已證實缺陷：

- 社交功能使用率「低於 2%」：報告沒有提供實際分析資料。
- 音訊一定佔用 15 至 30 MB 並造成 OOM：需要瀏覽器 memory profile。
- `stop()` 必然造成 DAC 爆音：可能發生 click，但必須用實際音訊與設備測試。
- 圖譜 300 節點一定掉到 10 至 15 FPS：需要 Playwright/Performance trace，不能只靠 DOM 數量推算。
- AI 變形題能帶來「超越市場 99%」：沒有可驗證基準。
- 必須導入 IRT/Elo/CAT：目前缺少題目難度、使用者能力與足夠答題樣本，先做規則式難度分層較合理。
- Swipe card、卡片物理動畫：屬產品偏好，不是現有系統缺陷。
- `Graph -> AI 出題 -> Quiz -> Heatmap`：方向有價值，但資料模型、題目與節點的關聯尚未存在，開發成本很高，不應列為近期 P0。
- LocalStorage 5 MB：風險真實，但實際是否達到 quota 必須依圖片數量、壓縮後大小與瀏覽器測量；先加入容量監控與失敗提示，再考慮 IndexedDB。
- SSRF：瀏覽器直接呼叫使用者自訂 `baseUrl` 與典型伺服器 SSRF 不同。這比較是「使用者可控制的瀏覽器網路請求／CORS 限制」風險，不應直接標為 P0 SSRF。

## 四、建議的實際優先順序

### P0：立即修正

1. 到期複習真正入口
2. 測驗結束、重做、退出的統計結算流程，並加上 idempotency 防止重複記錄

3. BOM 清理與 Blob 匯出
4. 補 QuizCard、快捷鍵、FocusTimer 的核心測試
5. 成就系統隱藏未實作項目或補上少數真正重要事件
6. 題庫搜尋與簡單篩選
7. 穩定題目選項洗牌

6. 社交系統重做或 URL 分享

8. Canvas/WebGL 圖譜渲染

**最終判定：**這份報告約有一半以上的核心方向是正確的，尤其是 SM-2 入口、統計漏記、快捷鍵、成就、資料驗證、時區與匯出問題。但它把許多「合理風險」寫成「已發生的 P0 災難」，也有若干已過時描述。建議把它當作候選 backlog 與問題線索，不要直接依照原本的 P0/P1 排程全面實作。
