# OpenSpec Apply with Tests — Implementation + Stress Test Integration

## Overview

This skill combines TWO workflows into a single implementation pass:
1. **Standard OpenSpec Apply** — Execute tasks from `tasks.md` (identical to `openspec-apply-change`)
2. **Stress Test Integration** — Read `stress-test-report.md` and `benchmark-harness.md` (if they exist) and use them as supplementary guidance during implementation

The stress test artifacts are **OPTIONAL**. If they don't exist, this skill behaves identically to the standard `openspec-apply-change` skill.

## ABSOLUTE RULES

> **RULE-01**: NEVER modify `stress-test-report.md` or `benchmark-harness.md` — they are READ-ONLY references.
> **RULE-02**: NEVER skip standard tasks in favor of stress test items. Standard tasks come FIRST.
> **RULE-03**: Stress test findings are ADVISORY — implement them as defensive improvements alongside standard tasks, not as replacements.
> **RULE-04**: All commands are for Windows (pwsh). Use backslash paths.

---

## Execution Pipeline

```
Phase 1: SELECT → Phase 2: DETECT → Phase 3: INGEST → Phase 4: IMPLEMENT → Phase 5: REPORT
```

### Phase 1: SELECT — Identify the Target Change

1. If a name is provided, use it directly.
2. If no name is provided:
   - Infer from conversation context if the user mentioned a change
   - Auto-select if only one active change exists
   - If ambiguous, run `openspec list --json` and ask the user to select
3. Announce: "Using change: `<name>`"

### Phase 2: DETECT — Check for Stress Test Artifacts

After identifying the change, check for the existence of stress test files:

```
openspec\changes\<name>\stress-test-report.md   ← Stress Test Report + Test Matrix
openspec\changes\<name>\benchmark-harness.md     ← Performance Benchmark Harness
```

**Detection Results**:

| stress-test-report.md | benchmark-harness.md | Mode |
|-----------------------|---------------------|------|
| ✅ Exists | ✅ Exists | **FULL TEST MODE** — All stress test guidance active |
| ✅ Exists | ❌ Missing | **PARTIAL TEST MODE** — Only stress test issues + test matrix active |
| ❌ Missing | ✅ Exists | **PARTIAL TEST MODE** — Only benchmark guidance active |
| ❌ Missing | ❌ Missing | **STANDARD MODE** — Identical to standard openspec-apply-change |

**Announce the detected mode** to the user:
- `🧪 FULL TEST MODE: Stress test artifacts detected. Implementation will incorporate test findings.`
- `🧪 PARTIAL TEST MODE: Only <file> found. Partial test guidance active.`
- `📋 STANDARD MODE: No stress test artifacts found. Using standard apply flow.`

### Phase 3: INGEST — Read All Context

**Standard artifacts** (always read):
1. Run `openspec status --change "<name>" --json`
2. Run `openspec instructions apply --change "<name>" --json`
3. Read all files listed in `contextFiles`: proposal.md, design.md, tasks.md, specs/*.md

   **Handle states:**
   - If `state: "blocked"`: show message, suggest creating missing artifacts first
   - If `state: "all_done"`: congratulate, suggest archive
   - Otherwise: proceed

**Stress test artifacts** (read if detected in Phase 2):
4. If `stress-test-report.md` exists:
   - Read it completely
   - Extract the **Issues List** (all `[ISSUE-XXX]` entries)
   - Extract the **Test Matrix** (all module test case tables)
   - Build a mapping: `task group → related stress test issues`
5. If `benchmark-harness.md` exists:
   - Read it completely
   - Extract the **Performance Baselines** for each module
   - Extract the **Regression Gates** (acceptable thresholds)

### Phase 4: IMPLEMENT — Execute Tasks with Test Awareness

**For each pending task in tasks.md**, follow this enhanced loop:

#### Step A: Show task context
```
## Implementing: <change-name> (schema: <schema-name>)
### Mode: 🧪 FULL TEST MODE | 📋 STANDARD MODE

Working on task N/M: <task description>
```

#### Step B: Check for related stress test issues
- If in TEST MODE, check if any `[ISSUE-XXX]` from `stress-test-report.md` references this task group
- If related issues exist, display them:
  ```
  ⚠️ Related Stress Test Issues:
  - [ISSUE-003] Logic Gap: <description> (Risk: HIGH)
  - [ISSUE-007] Edge Case: <description> (Risk: MEDIUM)
  ```

#### Step C: Implement the task
- Make the code changes required by the task
- **If in TEST MODE**: While implementing, proactively address any related HIGH-priority stress test issues:
  - Add error boundaries / try-catch blocks where ARCHITECTURE issues were flagged
  - Add null checks / guard clauses where LOGIC GAP issues were flagged
  - Add input validation where EDGE CASE issues were flagged
  - These additions should be NATURAL to the implementation, not forced

#### Step D: Check for related test cases from the Test Matrix
- If in TEST MODE, check if the Test Matrix has test cases for this module
- If relevant P0 test cases exist, flag them:
  ```
  📋 Related P0 Test Cases (consider validating):
  - should_<action>_when_<condition>
  - should_<action>_when_<condition>
  ```

#### Step E: Mark task complete
- Update tasks.md: `- [ ]` → `- [x]`
- Show: `✓ Task complete`

#### Step F: Continue to next task

**Pause if:**
- Task is unclear → ask for clarification
- A HIGH-priority stress test issue conflicts with the task design → report the conflict
- Error or blocker encountered → report and wait
- User interrupts

### Phase 5: REPORT — Final Summary

**Output On Completion:**

```markdown
## Implementation Complete

**Change:** <change-name>
**Schema:** <schema-name>
**Mode:** 🧪 FULL TEST MODE | 📋 STANDARD MODE
**Progress:** N/M tasks complete ✓

### Completed This Session
- [x] Task 1
- [x] Task 2
...

### Stress Test Integration Summary (if TEST MODE)
- **Issues Addressed**: X/Y HIGH issues proactively handled
- **Issues Deferred**: Z issues (LOW priority, deferred to future)
- **P0 Test Cases**: N test cases flagged for validation

### Recommended Next Steps
1. Run `/opsx:verify` or `/auto-verify` to validate implementation
2. If stress test artifacts exist, verification skills will automatically audit them
3. When ready, archive with `/opsx:archive`
```

**Output On Pause:**

```markdown
## Implementation Paused

**Change:** <change-name>
**Mode:** <mode>
**Progress:** N/M tasks complete

### Issue Encountered
<description>

### Stress Test Context (if relevant)
<related stress test issue that may have caused the conflict>

**Options:**
1. <option 1>
2. <option 2>
3. Other approach
```

## Guardrails

- Keep going through tasks until done or blocked
- Always read context files before starting
- In TEST MODE, stress test issues are ADVISORY — do NOT block task completion for LOW-risk issues
- HIGH-risk stress test issues should be addressed if naturally possible; otherwise flag for user
- If task is ambiguous, pause and ask before implementing
- Keep code changes minimal and scoped to each task
- Update task checkbox immediately after completing each task
- On errors/blockers, pause — don't guess
- NEVER modify the stress test artifact files

## Graceful Degradation

| Scenario | Behavior |
|----------|----------|
| No stress test files exist | Behaves identically to standard apply |
| Stress test file is malformed | Skip it with a WARNING, continue in STANDARD MODE |
| openspec CLI unavailable | Fall back to manual file reading |
| Task has no related stress test issues | Implement normally without extra steps |
